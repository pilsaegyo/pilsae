# 필새 영상 아카이브 — 날짜 자동 재분석 버전

`videos.json` 원본을 매번 그대로 읽은 뒤 `description + source + title` 전체를 다시 분석하여 날짜를 추출합니다.

## 인식 형식
- `150227` → 2015-02-27
- `010826` → 2001-08-26
- `20010812` → 2001-08-12
- `2015.02.27`
- `2015-02-27`
- `2015/02/27`
- `2015년 2월 27일`
- `2000.06` → 화면에는 2000.06, 내부 정렬값은 2000-06-01
- `2000년 6월` → 화면에는 2000.06
- `00\`` → 화면에는 2000년, 내부 정렬값은 2000-01-01
- `99\`` → 화면에는 1999년
- `1999\`` → 화면에는 1999년
- `99년도`, `1999년` → 연도만 적용

## 2자리 연도 변환 규칙
- 00~29 → 2000~2029
- 30~99 → 1930~1999

## 연도/월만 있는 값 처리
실제 월/일을 알 수 없으므로 화면에는 없는 날짜를 만들지 않습니다.
정렬 및 연도 필터를 위해 내부값만 다음처럼 임시 처리합니다.
- 연도만: YYYY-01-01
- 연/월만: YYYY-MM-01

## 혼합 영상
한 설명에서 2개 이상의 날짜가 추출되면 자동으로 `혼합 영상`으로 분류합니다.

## 정렬
1. 원본/설명에서 얻은 날짜 기준 내림차순
2. 같은 날짜면 YouTube 업로드 날짜 기준 내림차순

- `Ai 신혜성`

## 해시태그 날짜 제외
날짜 분석은 `description`에서만 수행하며,
`#`로 시작하는 해시태그 토큰은 분석 전에 제거합니다.

예:
- `#1999` → 날짜 인식 안 함
- `#2000년` → 날짜 인식 안 함
- `#2015-02-27` → 날짜 인식 안 함
- 일반 본문 `2015-02-27` → 날짜 인식함

## v8.1 날짜 정확도별 아카이브 그룹화
- `day`: 정확한 날짜의 해당 월에 배치.
- `month`: 해당 월에 배치하고 `일자 미상` 표시.
- `year`: 1월로 넣지 않고 해당 연도 하단의 `연도만 확인` 영역에 배치.
- `unknown`: 전체 아카이브 마지막의 `날짜 미확인` 영역에 배치.
- 연도만 있는 영상은 내부적으로 YYYY-01-01을 저장해도 화면 그룹화는 `precision` 기준으로 처리하므로 1월 영상으로 오해되지 않음.

## v10 날짜 인식 개선
- `08.11.08`, `08-11-08`, `08/11/08` 같은 `YY.MM.DD` 형식을 정확한 날짜로 자동 인식.
- `9905` 같은 4자리 `YYMM`은 자동 적용하지 않음. 설명의 한 줄 맨 앞에 있고 MM이 01~12일 때만 관리자 `날짜 후보`로 제시.
- 관리자가 `1999.05로 적용`을 누르면 Worker가 GitHub `data/videos.json`에 수동 월 날짜를 저장하고 재배포.
- `날짜 아님`을 누르면 해당 후보를 제외 목록에 저장해 다음 동기화 이후에도 다시 제안하지 않음.
- 수동 적용 날짜와 제외 후보는 YouTube 전체 동기화 시에도 보존.


## v10.1 제목 + 설명 날짜 후보
- 날짜 미확인 영상에 한해 제목도 관리자 검토 후보 탐색에 사용.
- 제목 `08.11.08 ...` → `2008.11.08` 후보(자동 확정 아님).
- 제목 `081108 ...` → `2008.11.08` 후보.
- 제목 `9905 ...` → `1999.05` 후보.
- 설명의 `YY.MM.DD`는 기존처럼 자동 확정.
- 설명의 `YYMM` 4자리는 보수적으로 줄 맨 앞에서만 월 후보 생성.
- 관리자 화면에 `제목에서 발견` / `설명에서 발견` 배지 표시.
- 제목에서 나온 날짜는 반드시 관리자가 `적용`해야 실제 아카이브 날짜가 됨.

- `새 설명 날짜 사용` 버튼으로 새 설명 기준을 확정 가능.
- 새 수동 날짜를 다시 입력하면 검토 상태가 자동 해제됨.

## v27.0-auto-sync-diagnostics · 자동 동기화 실패 진단 / Cron 재등록
### 문제
- 수동 YouTube 미리보기에서는 신규 영상이 정상 감지되었으나, 20:00 Cron 자동 동기화가 실행되지 않은 상태를 확인.
- 기존 자동 실행 함수가 오류를 `catch`한 뒤 다시 throw하지 않아 실제 실패가 발생해도 scheduled invocation이 실패로 명확하게 남지 않을 수 있었음.

### 수정
- `worker/wrangler.jsonc`에 Cron Trigger를 다시 명시:
  - `0 11 * * *` = 매일 20:00 KST YouTube 자동 동기화
  - `0 18 * * 6` = 매주 일요일 03:00 KST 주간 백업
- Workers Observability 로그 저장을 명시적으로 ON (`enabled: true`, sampling 100%).
- scheduled handler가 자동 작업을 `await`하도록 변경.
- 자동 동기화/주간 백업 실패를 더 이상 삼키지 않고 다시 throw하여 Workers Logs에 실패 invocation으로 남도록 수정.
- 알 수 없는 Cron 표현식이 들어오면 성공 처리하지 않고 오류로 기록.

### 관리자 진단
- 영상 동기화 탭에 `자동 동기화 실행 준비 정상/확인 필요` 진단 영역 추가.
- ADMIN_TOKEN / YOUTUBE_API_KEY / GITHUB_TOKEN 존재 여부를 Worker에서 점검.
- 배포 설정 기준 Cron 시간, 최근 자동 반영 이력, 최근 데이터 반영 시각을 표시.
- `자동 동기화 지금 실행` 버튼 추가.
  - 실제 20:00 Cron과 동일한 preview → 변경 확인 → apply 로직 실행.
  - 변경이 없으면 GitHub 데이터 변경 없이 종료.
  - 변경이 있으면 기존 백업/수동값 보존/동기화 로직을 그대로 사용.
- 자동 실행으로 변경이 적용된 경우 변경 이력에 `auto_sync_apply`로 구분 기록.
- 수동 진단 버튼으로 적용된 경우 `auto_sync_test_apply`로 구분 기록.

### 참고
- 변경이 전혀 없는 Cron 실행은 기존 원칙대로 GitHub 커밋/Cloudflare 재배포를 만들지 않음.
- 따라서 '변경 없음' 실행 기록의 장기 보관은 Workers Logs에서 확인함.

## v27.2-sync-live-refresh · 자동 동기화 후 공개 사이트 반영 확인
### 확인된 현상
- 자동 동기화 성공 응답과 GitHub 데이터 커밋은 완료됐지만, 현재 브라우저에 로드된 관리자 데이터/공개 사이트 정적 asset은 즉시 갱신되지 않을 수 있음.
- 기존 UI가 GitHub 커밋 성공을 곧바로 '데이터 반영 완료'처럼 보여 실제 공개 사이트 반영 여부와 혼동될 수 있었음.

### 수정
- `자동 동기화 지금 실행` 성공 후 GitHub 반영과 공개 사이트 반영을 분리해서 표시.
- GitHub 적용 후 공개 사이트의 `data/videos.json`을 cache-buster와 `no-store`로 주기적으로 확인.
- 신규 영상 ID와 목표 총 영상 수가 실제 공개 `videos.json`에서 확인된 뒤에만 `사이트 반영 완료` 표시.
- 공개 사이트 반영 확인이 끝나면 현재 관리자 페이지의 메모리 데이터도 즉시 다시 로드하여:
  - 전체 영상 수
  - 새 검토 건수
  - 날짜 검토
  - 콘텐츠 분류 목록
  을 새 데이터 기준으로 재렌더링.
- 3분 안에 공개 사이트에 새 데이터가 보이지 않으면:
  `GitHub에는 정상 반영됐지만 공개 사이트에 아직 배포되지 않음`
  으로 명확하게 안내.
- 진단 문구에서 관리자 버튼으로 실행한 건은 `최근 자동 테스트`,
  실제 Cron이 적용한 건은 `최근 Cron 자동 반영`으로 구분.

### 중요
자동 동기화는 두 단계임:
1. Worker가 GitHub `data/videos.json` 갱신
2. GitHub 변경을 Cloudflare 공개 사이트가 배포

1번이 성공해도 2번이 완료되기 전까지 현재 공개 사이트에서는 이전 데이터를 볼 수 있음.


## v27.3-visitor-analytics · 방문 통계 (IP 해시 기반)
### 저장 방식
- 공개 사이트 첫 로드 시 Admin Worker의 `/track-visit`로 1회 전송.
- 원본 IP는 데이터베이스에 저장하지 않음.
- Worker가 `CF-Connecting-IP + ADMIN_TOKEN`을 SHA-256으로 익명화해 `V-XXXXXXXXXXXX` 형태의 방문자 ID만 저장.
- 같은 IP의 30분 이내 재접속은 같은 방문 세션으로 보고 중복 집계하지 않음.
- 검색/필터/보기 전환은 SPA 내부 동작이라 추가 방문으로 집계하지 않음.
- 일반적인 bot/crawler User-Agent는 집계에서 제외.

### 관리자
- 대시보드: 오늘 방문 / 오늘 순 방문자 / 최근 7일 방문 / 최근 90일 순 방문자.
- `방문 통계` 탭 추가.
- 최근 14일 일별 방문·순 방문자, 최근 90일 방문 많은 익명 방문자, 최근 50건 방문 내역 표시.
- 원본 IP 주소는 관리자에서도 확인할 수 없음.

### 개인정보 최소화
- 방문 이벤트와 익명 방문자 식별자는 최근 90일만 보관.
- 매주 일요일 주간 백업 Cron 실행 후 90일 초과 방문 기록을 자동 삭제.
- IP 기반 수치는 동일 공유 IP(NAT)는 한 명처럼 보일 수 있고, IPv6 주소 변경은 다른 방문자로 보일 수 있으므로 '추정 순 방문자' 성격임.

### Cloudflare D1
- `worker/wrangler.jsonc`에 `VISITOR_DB` D1 binding 추가.
- Wrangler 자동 리소스 프로비저닝을 사용하여 첫 Worker 배포 시 D1 데이터베이스가 자동 생성/연결됨.
- 테이블/인덱스는 Worker가 첫 사용 시 자동 생성.
- 500명 안팎 규모에서는 D1 Free 한도(2026-09 기준 5M rows read/day, 100k rows written/day)에 비해 매우 작은 사용량.
